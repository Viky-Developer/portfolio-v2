# VIGNESH.DEV --- Portfolio Build Specification

> **Core idea:** A professional personal portfolio designed as a modern
> engineering workspace.
>
> **UX principle:** **Developer-inspired visually. Normal website
> behavior functionally.**
>
> The site should be immediately understandable to HR/recruiters, while
> developers discover deeper Git, Markdown, YAML, repository,
> API-console, and terminal-inspired details.

---

## 1. Portfolio Identity

**Name:** Vignesh S.\
**Role:** Backend Software Engineer\
**Specialization:** Payment Systems & FinTech\
**Location:** Chennai, India

### Positioning

> **Building reliable systems behind digital payments.**

Supporting copy:

> I build backend and payment infrastructure using Go, with a focus on
> reliability, performance, and distributed systems.

The portfolio must communicate:

> **An engineer who builds reliable backend and payment systems.**

This is **not** an AI-themed portfolio and must not look like a generic
developer template, SaaS landing page, gaming UI, cyberpunk interface,
VS Code clone, or GitHub clone.

---

## 2. Unified Concept

Build the entire portfolio around one coherent concept:

# **VIGNESH.DEV --- Personal Engineering Workspace**

Take subtle inspiration from:

- Markdown / README documentation
- Git history
- Code repositories
- YAML configuration
- API clients
- Request traces / observability
- Terminal interfaces
- Technical documentation

Do **not** make every section look like a different application.

Instead, extract the shared visual language of developer tools:

- precise spacing
- thin borders
- technical metadata
- restrained monospace typography
- status indicators
- clear information hierarchy
- flat surfaces
- meaningful state colors

The normal navigation must remain obvious:

**About · Experience · Projects · Stack · Background · Contact ·
Resume**

Never require visitors to:

- type terminal commands
- understand YAML
- understand Git
- open fake files
- use keyboard shortcuts
- navigate an IDE-style file tree

Developer metaphors are presentation devices, not navigation
requirements.

# 4. Color System --- Deep Forest / Charcoal / Warm Cream

Use the visual direction from the approved portfolio concept: a **deep
forest-charcoal engineering interface with warm cream typography and
restrained sage-green accents**.

The site should feel mature, calm, technical, handcrafted, and premium
--- not like an AI-generated SaaS dashboard.

## Color Philosophy

This is **not a bright green portfolio**.

The interface should be approximately:

- **88%** deep forest/charcoal neutrals
- **9%** warm cream/gray typography
- **3%** sage accent

The green should feel naturally embedded into the dark forest background
rather than glowing on top of it.

### Sage accent means

Use sage only for:

- active navigation
- current Git timeline node
- primary CTA
- selected tab
- important metric emphasis
- subtle link hover
- terminal cursor
- successful API state
- small availability/status indicator

### Warm Cream means

Use Warm Cream for:

- major headings
- role titles
- important values
- primary readable content

This prevents the site from looking harsh black-and-white.

### Secondary and muted tones

Use Soft Stone and Sage Gray for:

- descriptions
- dates
- metadata
- inactive navigation
- previous timeline nodes
- secondary labels

### Terracotta

Use Muted Terracotta extremely sparingly and only where a
negative/downward engineering metric genuinely benefits from
differentiation.

Do not use it as a decorative accent.

## No Bright White Bars

Do **not** introduce pure-white section backgrounds, white horizontal
bars, white cards, or abrupt light bands between sections.

All sections should flow continuously through the same deep
forest/charcoal environment.

Separation should come from:

- whitespace
- thin dark-sage dividers
- subtle surface shifts
- typography hierarchy

not from bright background changes.

## Strictly Avoid

- pure white backgrounds
- sage blue
- bright orange
- purple
- pink
- neon green
- neon cyan
- blue/purple gradients
- colorful gradients
- green glow
- glassmorphism
- neon borders
- colorful blobs
- oversized shadows

The final color impression should be:

> **deep forest + charcoal + warm paper typography + restrained sage**

It should feel like a carefully designed engineering
publication/workspace, not an AI product template.

# 4A. Approved Visual Direction

Use the generated full-page concept as the visual reference for the
overall mood:

- deep green-black canvas
- warm cream editorial headings
- muted gray-green body copy
- thin sage/dark-moss dividers
- restrained green active states
- spacious desktop composition
- minimal rectangular controls
- Git timeline integrated into the page rather than boxed into cards
- project/API panels that are darker than the page but still belong to
  the same palette
- technical details that feel embedded rather than decorative

## Important: Keep the Page Continuous

The website should feel like **one long engineered document**.

Do not alternate between unrelated section background colors.

Do not use bright separators.

A section transition should look approximately like:

```text
deep forest canvas

01 / HOME
content...

──────────────────────────────────── subtle dark-sage divider

02 / ABOUT
content...

──────────────────────────────────── subtle dark-sage divider

03 / EXPERIENCE
content...
```

This continuity is essential to the approved visual identity.

## Cards

Use cards only where the information genuinely behaves like a contained
tool:

- repository/project preview
- API request/response console
- terminal contact panel

Do **not** put About, Experience, Education, metrics, or every skill
inside individual cards.

Typography, alignment, whitespace, and thin dividers should do most of
the layout work.

- Geist Mono

  │

  │

  │

  │

### Color semantics

`POST` → Soft Sage\

# 15A. Visual Density & Noise Control

The developer-workspace concept must be expressed through **structure
and details**, not through dozens of colored micro-components.

Reduce:

- small boxes
- badges
- colored labels
- bordered tags
- status indicators
- tiny metric cards
- accent-colored separators
- cards inside cards

Prefer:

- typography
- whitespace
- alignment
- thin neutral separators
- subtle surface changes
- one clear accent state at a time

Do not put every technology inside a colored pill.

Do not use a colored border around every component.

Do not make every section look like a dashboard widget grid.

The design should become visually quieter as the viewport gets smaller.

---

# 16. Motion System

Motion should communicate **state**, not decorate the website.

## Allowed

- subtle active navigation indicator
- smooth section transitions
- gentle repository hover
- terminal cursor blink
- API request execution
- request trace progression
- Git timeline activation while scrolling
- subtle status indicator
- restrained number transitions
- small focus/hover transitions

## Avoid

- 3D models
- rotating objects
- particles
- floating cards
- mouse trails
- scroll-jacking
- giant parallax effects
- animated gradients
- excessive typewriter effects
- glowing UI
- constant pulsing
- bouncing icons

Respect `prefers-reduced-motion`.

# 17. Responsive Design --- Mobile Must Feel Editorial

The mobile portfolio must **not** look like a compressed IDE, terminal,
or monitoring dashboard.

Mobile should feel like a **premium editorial portfolio with
developer-tool details**.

## Mobile principles

- use a normal vertical navigation/menu
- increase vertical whitespace significantly
- allow sections to extend naturally instead of fitting everything
  above the fold
- do not shrink typography just to display more content
- stack information vertically
- simplify the Git timeline while preserving the history metaphor
- keep current/previous role distinction clear
- keep core content free from horizontal scrolling
- allow code/YAML areas to scroll only when technically necessary
- keep CTAs obvious and touch-friendly
- use fewer borders, badges, chips, and mini-panels than desktop

## Metrics on mobile

Do **not** use three-column metric cards.

Prefer:

```text
45% ↓
Database read latency

────────────────────────

60% ↓
Relational query load

────────────────────────

30% ↓
Dispute-resolution turnaround
```

Let typography and spacing create hierarchy.

## Projects on mobile

Separate the project overview from the technical demonstration.

The main project section should show:

```text
URL SHORTENER

High-concurrency URL shortening
service built with Go.

Go · Redis · PostgreSQL

< 10ms
Redirect latency

Base62 encoding
Rate limiting
Link expiration
Click analytics

[ Explore Project ]
```

The **Explore Project** interaction/page should contain:

- API Console
- Request
- Response
- Request Trace
- deeper technical details

Do not place the full API console and request trace directly below an
already dense repository card.

## Developer metaphors on mobile

Simplify them rather than compressing them.

The user should first see a readable portfolio and only then notice the
README, Git, repository, YAML, API, and terminal inspiration.
